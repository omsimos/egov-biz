## Context

Add eGov SSO to `apps/egov-biz`, replacing its hardcoded citizen identity and image with authenticated staging data. The original brief asked for a dropdown of the portal's test users whose Login button would automatically generate and exchange a code; refresh persistence was then made explicit. The login surface was later asked to follow the supplied eGov MPIN-style reference while using one input instead of OTP boxes. The scope expanded to exercising the authenticated Business chat and adding a `user_info` tool so verified eGov data could prefill later forms.

The user then supplied a fixed BIR Form 1901 PDF and asked for an explicitly invoked `generate_bir_form` tool. It was to reuse authenticated `user_info`, stamp every applicable profile field into the template, return a PDF artifact in chat, and open an in-app preview when selected. A Bun/TypeScript pilot and a type-complete synthetic profile were also requested to calibrate and exercise the form before integrating the tool.

## Decisions

- **Use the supported exchange-code flow instead of reproducing the requested test-user dropdown.** Capturing the portal request showed that Generate is an authenticated, deployment-specific Next.js Server Action, not a documented eGov SSO endpoint, and redirects to portal login outside that session. Proxying portal cookies or hardcoding its rotating action hash was rejected as brittle and unsupported. The shipped login therefore accepts the official widget callback or a fresh portal-generated one-time code, then exchanges it server-side through the eGov package ([login screen](../apps/egov-biz/src/components/login-screen.tsx), [exchange route](../apps/egov-biz/src/app/api/auth/egov/exchange/route.ts)).

- **Keep the authenticated identity behind an opaque server session.** Browser-side access-token or raw-profile persistence was set aside so exchange codes, access tokens, partner secrets, and the complete profile would not enter browser storage. An `HttpOnly`, `SameSite=Lax` cookie identifies a process-local session; the client receives only the mapped fields needed by the app, while profile media is served through an authenticated, no-store proxy ([session store](../apps/egov-biz/src/lib/auth/session.ts), [profile mapper](../apps/egov-biz/src/lib/auth/profile.ts), [avatar route](../apps/egov-biz/src/app/api/auth/avatar/route.ts)). A durable shared store was not added because this is a hackathon sample; the stated boundary is that refresh survives while the server process lives, but a restart does not.

- **Require a browser-bound login intent and consume exchange codes only through same-origin POST.** A direct GET callback and an exchange endpoint without browser binding were implemented during iteration but removed after they were identified as login-CSRF/session-replacement paths. The final flow issues a five-minute HMAC-signed intent cookie, rejects cross-origin initiation or exchange, consumes the intent after successful login, and restores the authenticated UI with a full navigation so the widget is not left mounted in an authenticated session ([intent implementation](../apps/egov-biz/src/lib/auth/intent.ts), [intent route](../apps/egov-biz/src/app/api/auth/egov/intent/route.ts), [exchange route](../apps/egov-biz/src/app/api/auth/egov/exchange/route.ts)).

- **Make `user_info` a capability manifest, not a raw-profile tool.** The first implementation returned the complete profile requested by the brief, and an intermediate version returned an allowlisted subset. Both were set aside: the raw record included document identifiers, signatures, and base64 media, while exposing even selected values to the model could leak them through prompts, tool history, or responses. The shipped tool reports only which non-empty verified fields are available and their `eGov SSO` source; actual values remain in the authenticated server session and are applied by form tools. Model-visible form input/output substitutes placeholders for identity and address while the authenticated UI receives the populated form ([tool contract](../apps/egov-biz/src/lib/business-chat.ts), [chat route](../apps/egov-biz/src/app/api/agent/chat/route.ts), [field resolver](../apps/egov-biz/src/lib/form-prefill.ts)).

- **Treat a residential address as an explicit business-location choice, not a default.** Automatically falling back to the profile address, treating silence as consent, and inferring consent from free-form language were each rejected because a verified home address does not establish where a business operates. The agent now asks a structured “registered eGov address” versus “different address” question; an explicitly supplied business address wins, and ordinary-chat corrections are accepted only when parsed directly from the user's text. This keeps automatic verified prefill for applicable fields without asserting an unconfirmed business fact or marking an incomplete draft ready ([prefill rules](../apps/egov-biz/src/lib/form-prefill.ts), [prefill tests](../apps/egov-biz/src/lib/form-prefill.test.ts), [location resolution](../apps/egov-biz/src/lib/government-data.ts)).

- **Stamp and re-export the fixed four-page template instead of treating it as a fillable form or canvas image.** Inspection showed that the supplied PDF has no AcroForm fields, so native field filling was unavailable. Producing the final document from a browser canvas was set aside because it would rasterize the form, reduce print quality, increase file size, and make the added values non-selectable. The generator keeps the original template unchanged, overlays text, checkmarks, TIN groups, and the signature at calibrated PDF coordinates with `pdf-lib`, validates the expected four-page version, and saves a new PDF ([generator](../apps/egov-biz/src/lib/bir-form/generator.ts), [pilot script](../apps/egov-biz/scripts/generate-bir-1901.ts)).

- **Make `generate_bir_form` an invoke-only, no-input server tool that depends on the `user_info` capability manifest.** Passing citizen fields through model-generated tool arguments was rejected because it would move raw SSO values into the AI conversation. The tool requires `user_info` to be ready first, takes no profile input, reads the authenticated raw profile only on the server, and returns browser-safe artifact metadata rather than personal values or PDF bytes ([chat tool](../apps/egov-biz/src/app/api/agent/chat/route.ts), [artifact contract](../apps/egov-biz/src/lib/bir-form/artifact.ts), [tool types](../apps/egov-biz/src/lib/business-chat.ts)).

- **Store generated citizen PDFs inside the authenticated process-local session.** Writing the integrated tool's output to a public directory or returning base64 in chat was set aside so the PDF and its identity data would not become a public file or model-visible payload. Each session retains a bounded set of in-memory artifacts; an opaque artifact ID resolves only within that same session, and the authenticated endpoint serves the PDF with `private, no-store` caching for the card's preview, download, and full-screen actions ([session artifacts](../apps/egov-biz/src/lib/auth/session.ts), [artifact route](../apps/egov-biz/src/app/api/artifacts/bir-form/%5BartifactId%5D/route.ts), [preview UI](../apps/egov-biz/src/components/business-chat-screen.tsx)).

- **Normalize the SSO response as partial runtime data and prefill only recognizable values.** The first live generation crashed because staging omitted or returned `null` for fields the SDK had marked required. Keeping those required assumptions, coercing malformed objects into strings, or aborting the whole PDF when a signature could not be loaded were rejected. The public SSO types now make known fields optional/null-capable; both app and BIR mappers accept unknown runtime shapes, preserve valid nested values, accept TIN and foreign-address data only in recognizable forms, and leave malformed or source-less fields blank. Signature loading enforces format/size/transport checks but skips a failed image so the rest of the PDF can still be generated ([SSO types](../../egov.js/src/generated/types.gen.ts), [BIR profile mapper](../apps/egov-biz/src/lib/bir-form/profile.ts), [mapper tests](../apps/egov-biz/src/lib/bir-form/profile.test.ts), [PDF generator](../apps/egov-biz/src/lib/bir-form/generator.ts)).

- **Gate generation on an explicit request in the latest user message.** Proactively creating the PDF merely because BIR appears in a registration plan, or treating informational questions as generation requests, was set aside because the user required invocation only on request and the router could otherwise divert the message into ordinary intake. A deterministic intent check recognizes generate/create/prepare/fill/prefill instructions for BIR Form 1901, emits `user_info` first when needed, and then generates the artifact; questions such as “What is BIR Form 1901?” remain normal chat ([request gate](../apps/egov-biz/src/lib/bir-form/request.ts), [gate tests](../apps/egov-biz/src/lib/bir-form/request.test.ts), [router](../apps/egov-biz/src/app/api/agent/chat/route.ts)).

## Final state

`egov-biz` now has an eGov-styled login screen with a single masked exchange-code input and the official widget, server-side SSO exchange, refresh-restorable login/logout, live profile and avatar rendering, and authentication gates around profile, business, chat, and payment routes. The hardcoded citizen and business records are gone. Business chat can discover available verified profile fields and prefill DTI drafts server-side, with model redaction and explicit consent before reusing the registered address.

On an explicit generation request, chat now emits `user_info` followed by `generate_bir_form`, maps every recognizable SSO field into the configured four-page template, and returns a session-owned PDF artifact card. Selecting it opens an authenticated in-app preview with download and full-screen actions. Missing, null, opaque, or malformed profile values are skipped without discarding valid fields, and an invalid signature no longer prevents the draft from being generated. The checked-in Bun pilot can also generate conservative and type-complete synthetic fixture PDFs; generated files remain ignored.

The delivered login diverges from the requested test-user dropdown because the portal's generator is not an integrator-facing API; users must use the official widget or provide a fresh code generated in the authenticated portal. Session and PDF-artifact persistence are intentionally limited to the current server process. The requested raw-profile `user_info` JSON did not ship to the model: it became metadata-only because the record and populated tool history could expose sensitive identity data. BIR-only selections and other fields without an authoritative SSO counterpart remain blank rather than being inferred.
